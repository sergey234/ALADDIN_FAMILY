# Фаза 2 эксплуатации (OPS): распределённые лимиты, алерты, инвойс в БД, сторно, CI/CD

Документ фиксирует **план доработок** после закрытия основного бэклога (44 ID в `IMPLEMENTATION_PLAN_AND_TASKS.md` §3.0). Это **не обязательный** следующий релиз: внедрять по приоритету инфраструктуры и рисков.

**Связь с текущими ограничениями:** см. `docs/EDGE_CASES.md` §3.5–3.6 (in-memory rate limit и кулдаун инвойса, алерты как логи, ручное сторно). Канон деплоя: `docs/ML_SYSTEM_HANDOFF_FINAL.md`.

---

## 0. Цели и принципы

| Цель | Кратко |
|------|--------|
| Глобальные лимиты | Одинаковая политика при **нескольких** процессах Partner API |
| Алерты | Критичное доходит до дежурного **без** обязательного просмотра логов |
| Инвойс | Повторный счёт согласован между **всеми** инстансами бота (общая БД) |
| Сторно | Ближе к фактам провайдера, меньше ручной рутины **где API позволяет** |
| CI/CD | Воспроизводимый выкат с проверками и откатом |
| Break-glass governance | Ручной `adm:paidbg` используется только по чеклисту и с обязательным аудитом |

**Принципы внедрения**

- Флаги и **деградация**: при выключенном Redis / алертах — поведение как сейчас.
- Не класть секреты алертов в git; только `env.example` с плейсхолдерами.
- SQLite остаётся БД бота; Redis — **опционально** рядом.

## 1. Распределённый rate limit (Partner API)

### 1.1 Поведение и конфигурация

- Переменные: `PARTNER_API_RATE_LIMIT_BACKEND=memory|redis` (по умолчанию `memory`).
- При `redis`: `REDIS_URL` (или набор `REDIS_HOST`, `REDIS_PORT`, …).
- Смысл существующих `PARTNER_API_RATE_LIMIT_*` **не меняется**; меняется только хранилище счётчиков.
- Модель окна: зафиксировать в коде и доке (**fixed window 60 с** проще sliding без Lua).

### 1.2 Архитектура

- Абстракция `RateLimitStore` в `partner_api/` с реализациями `MemoryRateLimitStore`, `RedisRateLimitStore`.
- Middleware вызывает `check_and_consume(bucket_id, limit_per_minute)`.
- Ключи Redis: префикс `aladdin:rl:{class}:{id}` + TTL.

### 1.3 Поведение при падении Redis

- Рекомендация: **fallback на in-memory** в том же процессе + `WARNING` в лог + опциональный алерт (после реализации §2).
- Альтернатива **fail-closed** (503) — только если политика безопасности жёстче доступности.

### 1.4 Чеклист

- [ ] Интерфейс store + wiring в `rate_limit_middleware.py`
- [ ] Реализация Redis (async redis), конфиг в `Settings` / `env.example`
- [ ] Документировать семантику окна в `EDGE_CASES.md` §3.6
- [ ] Тесты: unit с fakeredis или мок клиента; ручной смоук «два воркера — один лимит»
- [ ] Runbook: установка Redis на сервере, мониторинг памяти, backup не обязателен для чистого rate-limit
- [ ] Nginx-level edge лимиты для webhook путей (IP burst + rate), чтобы снять пиковую нагрузку до Python/FastAPI

**Критерий готовности:** два процесса Partner API с общим Redis не могут суммарно превысить заданный порог в минуту (в пределах выбранной модели окна).

## 2. Алерты: Telegram и/или PagerDuty

### 2.1 Поведение

- Модуль `send_alert(severity, title, body, dedupe_key)` (размещение: `partner_api/` и/или `bot/services/` — избегать дублирования: один пакет `alerts_core` или общий модуль в `telegram_stars_shop_bot`).
- Если `ALERTS_ENABLED=false` — только лог (как сейчас).
- Если `true` — Telegram `sendMessage` и/или PagerDuty Events API v2.

### 2.2 Конфигурация (пример имён)

- [ ] `ALERTS_ENABLED`
- [ ] `ALERT_TELEGRAM_BOT_TOKEN`, `ALERT_TELEGRAM_CHAT_ID` (отдельный бот для ops — предпочтительно)
- [ ] `PAGERDUTY_ROUTING_KEY` (опционально)
- [ ] `ALERT_COOLDOWN_SECONDS` / дедуп по `dedupe_key` (Redis или LRU в процессе)

### 2.3 Точки интеграции (минимум)

- [ ] Рядом с существующим `WARNING` на ошибки вебхуков Partner API
- [ ] Рядом с логом «зависшие paid» (`stuck_orders_monitor`)
- [ ] Опционально: Redis недоступен (из §1)

### 2.4 Безопасность

- Не отправлять сырые тела вебхуков и PII; только: тип события, `order_id`, код ответа, короткий fingerprint.

### 2.5 Чеклист

**Критерий готовности:** при включённом флаге тестовый инцидент приводит к **одному** сообщению в канал дежурства за интервал cooldown.

## 3. Жёсткая политика повторного инвойса (SQLite)

### 3.1 Рекомендуемый вариант A

- Миграция `orders`: колонка `invoice_last_requested_at` (UTC ISO или `datetime('now')` в SQLite-стиле проекта).
- Опционально: `invoice_last_provider`, `invoice_last_external_id` — если API возвращает id счёта для поддержки.

## 4. Сторно / спор и провайдеры

### 4.1 Уровни

| Уровень | Содержание |
|---------|------------|
| L1 | Текущее: ручной супер-админ + аудит + runbook |
| L2 | Входящие события провайдера (если есть webhook/API refund/chargeback): подпись, idempotency, переход в `payment_disputed` или `refunded` по политике |
| L3 | Периодический reconciliation (только при наличии отчётного API) |

### 4.2 Безопасный путь для L2

- Сначала: событие → **только** `payment_disputed` + алерт + ссылка в админке «подтвердить» → `refunded`.
- После обкатки: узкий автоматический `refunded` только при однозначном контракте API.

### 4.3 Чеклист

- [ ] Исследование API LAVA / Crypto Pay / xRocket на предмет refund/cancel webhooks
- [ ] Таблица или расширение `payment_provider_events` типами событий
- [ ] Новый маршрут или расширение существующего вебхука + тесты идемпотентности
- [ ] Документ: матрица «событие провайдера → статус заказа»

**Критерий готовности:** повторная доставка того же события не меняет состояние повторно и не дублирует побочные эффекты.

## 5.5 Break-glass hardening (`adm:paidbg`)

### 5.5.1 Цель

- Убрать «человеческий free-pass»: ручной перевод crypto-заказа в `paid` только при недоступном webhook и только по подтверждённым фактам оплаты.

### 5.5.2 Минимальный регламент (боевой)

- [ ] Отдельный чеклист в `docs/RUNBOOK.md`: что проверяем до `adm:paidbg` (провайдер, invoice id, сумма, memo/payload, tx hash/receipt).
- [ ] Для `adm:paidbg` обязательные поля причины в `admin_audit_log.payload_json` (`reason_code`, `provider`, `external_invoice_id`, `evidence_ref`).
- [ ] Политика ролей: только `SUPER_ADMIN_IDS`; при наличии 2+ супер-админов — правило «вторые глаза» для сумм выше порога.
- [ ] Триггер алерта: каждый `adm:paidbg` отправляет уведомление в ops-канал (см. §2).
- [ ] Периодический отчёт (ежедневно/еженедельно): список break-glass операций и их исходы.

### 5.5.3 Критерий готовности

- Любой `adm:paidbg` имеет полный трассируемый след (кто, когда, почему, на каком основании), и может быть проверен постфактум без доступа к личным чатам оператора.

## 6. Порядок внедрения (рекомендуемый)

1. **§2 Алерты** — высокий ROI, мало риска для платежей.
2. **§3 Инвойс в БД** — усиливает деньги, не требует Redis.
3. **§5.5 Break-glass hardening** — до масштабирования, чтобы снизить риск «ручного paid без фактов».
4. **§1 Redis + edge rate limit** — когда появился Redis или решение его поднять **и** есть 2+ реплики API.
5. **§5 CI/CD** — когда стабильны тесты и нет срочных расхождений с ручным гайдом.
6. **§4 Сторно** — после спецификации API провайдеров и юридической уверенности в автоматах.

Зависимости: §1 опционально опирается на §2 (алерт при падении Redis). §4 может использовать §2 для эскалации.

## 7. Риски и откат (сводка)

| Блок | Риск | Откат |
|------|------|--------|
| §1 Redis | Единая точка отказа, latency | `BACKEND=memory`, мониторинг Redis |
| §2 Алерты | Спам, утечки метаданных | `ALERTS_ENABLED=false`, увеличить cooldown |
| §3 БД | Миграция на проде | бэкап `shop.db`, откат миграции |
| §4 Сторно | Ложный refund | только disputed + ручное подтверждение на первом этапе |
| §5 CI | Ошибочный rsync | жёсткие exclude как в handoff, ручной симлинк назад |
| §5.5 Break-glass | Ложный ручной `paid` | строгий чеклист + обязательный аудит + алерт + выборочный review |
