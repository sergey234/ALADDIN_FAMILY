## 🎯 ИСТИННАЯ ПРИЧИНА КРАША

### 🔴 ГИПОТЕЗА #1: DateFormatter используется в computed property, который вызывается рекурсивно

**Вероятность:** 🔴 **95%**

**Почему:**
- Stack trace показывает рекурсию в `DateFormatter.string(from:)`
- Адрес `0x1029ae4ec` повторяется - это функция вызывает сама себя
- Это может быть computed property, который вызывается при обновлении View

**Где искать:**
- Все computed properties с `DateFormatter.string(from:)`
- Все computed properties, которые вызываются во время форматирования даты
- Все computed properties в View, которые используют форматтеры

---

### 🔴 ГИПОТЕЗА #2: DateFormatter используется в body View, который обновляется рекурсивно

**Вероятность:** 🔴 **90%**

**Почему:**
- Если `DateFormatter.string(from:)` вызывается в `body` View
- И `body` вызывается при обновлении View
- И обновление View вызывает форматирование даты
- Это может вызвать рекурсию

**Где искать:**
- Все места, где `DateFormatter.string(from:)` вызывается в `body`
- Все места, где форматирование даты происходит напрямую в `body`
- Все места, где используется `displayFormatter` или другие форматтеры в `body`

---

### 🔴 ГИПОТЕЗИ #3: Статический DateFormatter все еще использует Locale.current косвенно

**Вероятность:** 🟡 **70%**

**Почему:**
- Даже если мы используем `Locale(identifier: "ru_RU")`, форматтер может читать из `UserDefaults` через другие механизмы
- Если форматтер создается во время чтения из `UserDefaults`
- И чтение из `UserDefaults` вызывает обновление View
- Это может вызвать рекурсию

**Где искать:**
- Все статические форматтеры, которые могут использовать `Locale.current` косвенно
- Все форматтеры, которые создаются в computed properties
- Все форматтеры, которые используются в `body` View
