**Статус:** ✔️ План утверждён, готов к реализации

---

## 1. Цели и ограничения
- Выполнить требования Apple (Guideline 3.1.1) и убрать продажу цифрового контента из iOS-приложения.
- Сохранить гибкие способы оплаты для пользователей из РФ и других стран.
- Ничего не удаляем — код StoreKit/QR просто скрываем в App Store билде, оставляя для Android/RuStore.
- На сайте не требуется сбор персональных данных: оплата → генерация кода → пользователь вводит код в приложении.
- Бэкэнд фиксирует факт оплаты от сайта и сохраняет код/срок действия. В приложении мы только активируем код, привязанный к семье/устройству.

---

## 2. Архитектура решений

| Слой | Что меняется |
| --- | --- |
| **Мобильное iOS-приложение** | Информирует об оплате на сайте → открывает Safari → принимает код активации. |
| **Сайт** | Единая точка оплаты с несколькими методами (QR/СБП, карты, SberPay, Tinkoff Pay, прямой перевод). После оплаты — показ/отправка кода. |
| **API (бэкэнд)** | Получает подтверждение оплаты с сайта, генерирует код активации. Мобильное приложение проверяет и активирует код. |

---

## 3. UX‑поток пользователя
1. Пользователь нажимает в приложении «Оформить на сайте».
2. Приложение открывает сайт (Safari) с выбранным тарифом.
3. На сайте пользователь выбирает подходящий способ оплаты (QR/СБП, карта, SberPay, Tinkoff Pay, прямой перевод).
4. После успешной оплаты сайт показывает код активации (опционально дублирует через SMS/email в будущем, но это не обязательно).
5. Пользователь возвращается в приложение → «Активировать код» → вводит код → получает доступ к подписке.

## 5. Способы оплаты на сайте

| Способ | Комментарий |
| --- | --- |
| **QR/СБП** | Динамические QR через собственные интеграции топ‑банков: Сбербанк, Тинькофф, Альфа, ВТБ, Газпромбанк, Россельхозбанк, Совкомбанк, Уралсиб, Райффайзен (RU), МКБ, Почта Банк, Промсвязьбанк, Росбанк, Ситибанк (RU), Хоум Кредит, МТС Банк, Открытие, Ренессанс Кредит, Русский Стандарт, Синара, Траст. Каждый банк ↔ собственный QR/ссылка в приложении банка. |
| **Банковские карты** | «Мир» (обязательно), а также разрешённые Visa/Mastercard через прямые интернет-эквайринги этих же банков. Для каждого банка — отдельный checkout/iframe/ссылка, чтобы не зависеть от агрегаторов. |
| **SberPay / Tinkoff Pay** | Официальные SDK и кнопки банков, вставляем на лендинг (без сторонних провайдеров). |
| **Прямой перевод** | Резерв: показываем реквизиты (ИНН, расчётный счёт, БИК). Пользователь делает перевод вручную; поддержка подтверждает и выдаёт код. |

Главное — всё происходит на сайте, без агрегаторов вроде ЮKassa/CloudPayments. Приложение только активирует код, что полностью совместимо с политиками Apple.

## 6. Принципы безопасности данных
- Мобильное приложение не собирает персональные данные. Имя/email в профиле по желанию пользователя, хранятся локально (`@AppStorage`).
- Сайт фиксирует только транзакцию и код доступа. Код — не персональные данные.
- API при активации кода привязывает его к `familyID`/`deviceID`, что позволяет управлять доступом без хранения ПДн.
- Все операции защищены HTTPS, логи платежей — только по ID/коду, без ФИО.

## 13. Варианты оплаты без ПДн

1. **Alias + PIN + redirect**: пользователь вводит alias (6+ символов) и PIN (4–6 цифр), выбирает тариф, нажимает «Оплатить» → перенаправляется на платёжную страницу банка/агрегатора. После успешного webhook сайт показывает код.
2. **Alias + PIN + встроенный виджет**: собственные чек-ауты банков (Сбер, Тинькофф, Альфа) без e-mail. Код показывается сразу после подтверждения.
3. **Alias + PIN + QR/СБП**: генерация динамического QR, пользователь сканирует, оплачивает, сайт получает webhook и показывает код.
4. **Alias + PIN + ручная оплата**: как резерв — показ реквизитов, форма “отправить чек/номер транзакции”. Поддержка руками подтверждает и выдает код.

На каждой кнопке указываем «Оплата означает согласие с условиями. Возврат средств не предусмотрен. Если платёж не прошёл — средства автоматически вернутся банком в течение 0–3 дней».

## 14. Возвраты, поддержка и alias + PIN

- **Получение/повторная выдача кода:** пользователь вводит alias + PIN → система показывает ранее оплаченный код или статус (активирован/просрочен).
- **Возврат:** денег не возвращаем (фиксируем в тексте). Исключение — если платёж не прошёл на стороне банка: в этом случае ждём автоматического возврата (обычно сразу, максимум 3 банковских дня). На сайте отдельный FAQ: «Если операция отклонена — деньги вернутся на карту автоматически».
- **Поддержка:** без e-mail. На сайте форма «Нужна помощь?» (alias + PIN + сообщение), либо кнопка «Открыть чат-бот в Telegram» (будет добавлен). SLA: в интерфейсе описываем, что поддержка отвечает в течение X часов.
- **Процедура при зависшем платеже:** инструкция в FAQ («Если в банке висит “обрабатывается”, ничего делать не нужно — обычно деньги возвращаются за несколько минут; если нет — напишите нам с alias + PIN и ID операции»).

## 18. API: спецификация оплаты и активации

### 18.1. Общие требования
- Все эндпоинты работают по HTTPS, JSON.
- Авторизация: сайт/админ используют `X-API-Key`, мобильное приложение — `Bearer` токен (выдаёт `AuthService`).
- Коды активации — строка из 12 символов (буквы + цифры), срок действия настраиваемый (например, 30 дней).
- Alias (userAlias) — 6–32 символа, латиница/цифры. PIN — 4–6 цифр.
- Статусы платежа: `created`, `awaiting_payment`, `paid`, `failed`, `refunded`.
- Статусы кода: `pending`, `active`, `redeemed`, `expired`.

### 18.2. Эндпоинты сайта (front → backend)

#### POST `/api/payments/create`
Создаёт намерение оплаты.
```json
{
  "tariffId": "family_12m",
  "userAlias": "familySmith",
  "pin": "1234",
  "paymentMethod": "qr_sbp"
}
```
Ответ:
```json
{
  "paymentId": "pay_123",
  "redirectUrl": "https://psp.example/checkout?token=...",
  "qrData": "<base64>",         // если выбран QR
  "expiresAt": "2025-11-20T12:00:00Z"
}
```
Сервер сохраняет: `paymentId`, `tariffId`, `userAlias`, `pinHash`, `status=created`.

#### GET `/api/payments/:paymentId/status`
Используется сайтом для опроса виджета/iframe (если нет вебхука).
Ответ:
```json
{
  "status": "paid",
  "activationCode": "ALDN-1234-5678"
}
```

### 18.3. Вебхуки от платёжного провайдера

`POST /api/payments/confirm`
```json
{
  "paymentId": "pay_123",
  "status": "paid",
  "amount": 4990,
  "currency": "RUB",
  "pspTxnId": "abc-456"
}
```
- Если `status=paid`: генерируем `activationCode`, создаём запись `ActivationCode`.
- Если `status=failed`: помечаем платёж как `failed`.
- Ответ 200: `{ "ok": true }`.

### 18.4. Повторная выдача / проверка кода (сайт)

`POST /api/activation/retrieve`
```json
{
  "userAlias": "familySmith",
  "pin": "1234"
}
```
Ответ:
```json
{
  "activationCode": "ALDN-1234-5678",
  "status": "active",
  "expiresAt": "2026-01-01T00:00:00Z"
}
```
Если код уже активирован → сообщаем дату активации и связанный `familyId`.

### 18.5. Мобильное приложение

#### POST `/api/activation/verify`
```json
{
  "code": "ALDN-1234-5678",
  "deviceId": "ios-abc",
  "familyId": "fam_001"
}
```
Ответ:
```json
{
  "tariffId": "family_12m",
  "status": "active",
  "expiresAt": "2026-01-01T00:00:00Z"
}
```

#### POST `/api/activation/activate`
```json
{
  "code": "ALDN-1234-5678",
  "deviceId": "ios-abc",
  "familyId": "fam_001"
}
```
Условия:
- Если `status=active` и срок не прошёл → помечаем как `redeemed`, привязываем к `familyId`, активируем подписку в системе.
- Если код уже `redeemed` или `expired` → возвращаем ошибку.

Ответ при успехе:
```json
{
  "success": true,
  "tariffId": "family_12m",
  "expiresAt": "2026-01-01T00:00:00Z"
}
```

#### POST `/api/activation/status`
Позволяет приложению получить текущие подписки (для экрана профиля). Возвращает список активных тарифов, дату окончания, историю последних операций.

### 18.6. Административные эндпоинты
- `GET /api/admin/payments?status=paid&alias=...` — поиск платежей для поддержки.
- `POST /api/admin/codes/:code/revoke` — отзыв кода (например, при ошибке).
- `POST /api/admin/payments/:id/resend` — повторная отправка кода (для ручного флоу).

Все админ-эндпоинты защищены VPN/IP-ограничением + `X-Admin-Key`.

### 18.7. Логирование и аналитика
- Каждое событие (`payment_created`, `payment_paid`, `code_generated`, `code_activated`, `activation_failed`) отправляем в аналитический пайп (например, ClickHouse/Amplitude) для построения конверсий.
- Сайт фиксирует `source` (utm/приложение, браузер) → передаём в `/payments/create`.
- Ошибки активации (неверный код, просрочен) логируются и отображаются в панели поддержки.

## 19. QA‑чеклисты (оплата и активация)

### 19.1. Сайт
1. **Переход из приложения**: проверяем, что кнопка «Оформить на сайте» открывает нужный тариф и передаёт `tariffId`.
2. **Форма alias + PIN**:
   - валидаторы (минимум 6 символов для alias, только латиница/цифры; PIN 4–6 цифр);
   - отказ при дубликате alias (если уже есть активный платеж).
3. **Способы оплаты**:
   - QR/СБП — генерация, скан, успешный webhook.
   - Карта/виджет — успешный платёж и возврат в случае отказа.
   - SberPay/Tinkoff Pay — редирект/кнопка работают, платеж подтверждается.
   - Ручной перевод — форма “загрузить чек” отправляет данные в поддержку.
4. **Показ кода**: после `status=paid` код отображается, кнопки “скопировать” и “инструкция” работают.
5. **Повторная выдача**: alias+PIN возвращают код и статус (активен/уже погашен).
6. **Тексты и предупреждения**: на всех CTA есть сообщение «Оплачивая, вы принимаете условия. Возврат не предусмотрен».
7. **FAQ/поддержка**: ссылки ведут на Telegram-бот/форму, ответы раскрываются.

### 19.2. Бэкэнд
1. `/payments/create` возвращает `paymentId`, сохраняет запись в БД.
2. Webhook `confirm` создаёт код, проверяем на повторную отправку (идемпотентность).
3. `retrieve` шифрует и сверяет alias+PIN (не хранит в открытом виде).
4. Логи событий отображаются в админ-панели.
5. Статусы в базе переходят: `created → paid → code_generated`.

### 19.3. Мобильное приложение
1. Экран «Активировать код»: валидация формата, ошибки «неверный код», «код просрочен», «код уже использован».
2. `verify` показывает тариф, срок действия, предупреждение если код активирован другой семьёй.
3. `activate` активирует подписку, UI обновляет статус, скрывает кнопку «Ввести код».
4. Повторный ввод того же кода выдаёт понятную ошибку.
5. Если устройство офлайн — корректная обработка (показ сообщения, без падений).

### 19.4. End-to-end сценарии
1. Пользователь оплачивает тариф → получает код → активирует → видит “Подписка активна”.
2. Пользователь оплачивает, но закрывает страницу до получения кода → возвращается → вводит alias+PIN → получает код.
3. Платёж отклонён банком → проверяем, что статус `failed`, код не генерируется, деньги возвращаются.
4. Поддержка вручную выдаёт код по alias+PIN → проверяем запись в логе.
