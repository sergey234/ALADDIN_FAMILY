## 📊 АНАЛИЗ ПАТТЕРНОВ ПРИ РАЗНОЙ НАГРУЗКЕ

| **Малая** (100, 10) | 0-7ms | 2-17ms | < 25ms | 10 запросов / 12 workers = 0.8 на worker ✅ |

**При большой нагрузке:**
- 1,000 запросов одновременно
- 12 workers
- **83.3 запроса на worker** - это слишком много!
- Каждый worker обрабатывает запросы последовательно (или с ограничениями)
- Результат: **очередь в workers** → Processing time: 2-2,848ms

## 🎯 ОКОНЧАТЕЛЬНАЯ ПРИЧИНА: НЕДОСТАТОЧНО WORKERS

### **ЧТО ПРОИСХОДИТ:**

1. **Приходит 1,000 запросов одновременно**
2. **12 workers обрабатывают запросы**
3. **1,000 / 12 = 83.3 запроса на worker**
4. **Каждый worker обрабатывает запросы последовательно** (или с ограничениями async)
5. **Запросы ждут в очереди** внутри worker
6. **Processing time: 2-2,848ms** - запросы ждут обработки
7. **Результат:** P95 = 8,500ms

### **АНАЛОГИЯ:**

**Как очередь в банке:**
- 12 кассиров (workers)
- 1,000 покупателей одновременно
- 83.3 покупателя на кассира
- Покупатели ждут в очереди перед кассиром
- Обслуживание быстрое, но очередь большая
- Результат: долгое ожидание

---

## 🔍 ДЕТАЛЬНЫЙ АНАЛИЗ

### **Почему 12 workers недостаточно?**

1. **Async операции все еще создают очередь:**
   - Даже с async/await, при большом количестве запросов создается очередь
   - Каждый worker может обрабатывать ограниченное количество запросов одновременно

2. **GIL (Global Interpreter Lock) в Python:**
   - Python имеет GIL, который ограничивает параллелизм
   - Даже с async, GIL может создавать узкие места

3. **Ограничения async event loop:**
   - Каждый worker имеет свой event loop
   - При большом количестве задач event loop может быть перегружен

- P95: с 8,500ms до < 500ms
