## 🎯 ЦЕЛЬ

Выявить точную причину краша Settings Screen на реальном устройстве в TestFlight.

## 📋 ШАГИ ДИАГНОСТИКИ

### Шаг 1: Сбор логов в TestFlight

1. **Откройте приложение в TestFlight**
2. **Перейдите в настройки**
3. **Дождитесь краша (если произойдет)**
4. **Скопируйте все логи из Console.app или Xcode**

**Что искать в логах:**
- `🔴 SETTINGS: body НАЧАЛО` - доходит ли выполнение до body
- `🔴 SETTINGS: onAppear вызван` - вызывается ли onAppear
- `🔴 SETTINGS: init: ВЫЗВАН` - вызывается ли init
- `КРИТИЧЕСКАЯ ОШИБКА` - любые критические ошибки
- `Использование памяти = X MB` - превышает ли 200 MB
- `ИСПОЛЬЗОВАН КЭШ` - работает ли кэширование

---

### Шаг 2: Анализ краша в Xcode Organizer

1. **Откройте Xcode → Window → Organizer → Crashes**
2. **Найдите последний краш Settings Screen**
3. **Проверьте:**
   - **Exception Type:** `EXC_BAD_ACCESS`, `EXC_CRASH`, `SIGABRT`
   - **Exception Subtype:** `KERN_INVALID_ADDRESS`, `KERN_PROTECTION_FAILURE`
   - **Stack Trace:** Какая функция вызвала краш

**Что искать:**
- `Thread 0 Crashed` - главный поток упал
- `SettingsScreen` - упоминание SettingsScreen в stack trace
- `localizationManager` - проблемы с локализацией
- `tariffManager` - проблемы с тарифом
- `calculatedProtectionLevel` - проблемы с вычислениями

---

### Шаг 3: Проверка памяти

**В логах ищите:**
```
🔴 SETTINGS: Использование памяти = X MB
```

**Анализ:**
- **< 100 MB:** ✅ Нормально
- **100-200 MB:** ⚠️ Высокое, но приемлемо
- **> 200 MB:** 🔴 Проблема с памятью (утечка)

**Если > 200 MB:**
- Проверьте, не создаются ли объекты в цикле
- Проверьте, не удерживаются ли view в памяти
- Проверьте, не создаются ли множественные sheet'ы одновременно

---

### Шаг 4: Проверка потоков

**В логах ищите:**
```
КРИТИЧЕСКАЯ ОШИБКА - вызван не на main thread
```

**Анализ:**
- Если есть такие сообщения - проблема с потоками
- Все операции должны быть на `[MAIN]`

**Решение:**
- Убедитесь, что все computed properties вызываются на main thread
- Используйте `DispatchQueue.main.async` для обновлений

---

### Шаг 5: Проверка инициализации

**В логах ищите:**
```
🔴 SETTINGS: init: ВЫЗВАН - НАЧАЛО СОЗДАНИЯ VIEW
🔴 SETTINGS: onAppear вызван
🔴 SETTINGS: navigationManager = ...
🔴 SETTINGS: localizationManager = ...
```

**Анализ:**
- Если `init` не вызывается - проблема с созданием view
- Если `onAppear` не вызывается - проблема с появлением view
- Если менеджеры `nil` - проблема с EnvironmentObject

---

### Шаг 6: Проверка кэширования

**В логах ищите:**
```
ИСПОЛЬЗОВАН КЭШ
calculatedProtectionLevel: НАЧАЛО вычисления
```

**Анализ:**
- Если `ИСПОЛЬЗОВАН КЭШ` - кэширование работает
- Если `НАЧАЛО вычисления` вызывается 10+ раз - кэширование не работает

**Решение:**
- Проверьте, что кэш обновляется правильно
- Проверьте, что `onChange(of: tariffManager.currentTariff)` вызывается

## 🔍 ЧАСТЫЕ ПРИЧИНЫ КРАША

### 1. EXC_BAD_ACCESS (KERN_INVALID_ADDRESS)

**Причина:** Доступ к неинициализированной памяти

**Что проверить:**
- EnvironmentObject не передан
- Доступ к nil объекту
- Доступ к освобожденной памяти

**Решение:**
- Проверьте, что все EnvironmentObject переданы
- Используйте безопасные проверки

---

### 2. EXC_CRASH (SIGABRT)

**Причина:** Исключение или assertion failure

**Что проверить:**
- Force unwrap (`!`)
- Array index out of bounds
- Assertion failure

**Решение:**
- Убедитесь, что нет force unwrap'ов
- Используйте безопасные проверки

---

### 3. EXC_BAD_ACCESS (KERN_PROTECTION_FAILURE)

**Причина:** Доступ к защищенной памяти

**Что проверить:**
- Доступ к @Published свойствам не на main thread
- Доступ к UI не на main thread

**Решение:**
- Убедитесь, что все обновления на main thread
- Используйте `DispatchQueue.main.async`
