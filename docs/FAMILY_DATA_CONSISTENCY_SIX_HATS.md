# Согласованность семьи: сервер ↔ мобильный клиент (6 шляп)

Краткая рамка для командных решений после инцидента «удаление на клиенте OK, в БД остался `MEM_*`, `family/add` → 403».

## Белая шляпа (факты)

- `DELETE /api/user/delete` ранее не менял PostgreSQL — клиент очищал локально, сервер оставался прежним.
- `POST /api/family/add` сравнивал «админа» с **последней** строкой `family_members` по `user_id`, а не с владельцем целевой семьи — при отсутствии родительской строки в этой семье возможен 403 при валидном JWT владельца.
- `family_members.user_id` может быть `NULL` у слота, добавленного родителем до логина ребёнка; `DELETE` пользователя не трогает такие строки без отдельной политики.
- Инвариант reconcile: одна строка `child` + владелец семьи — чинится; на **free** раньше не чинился placeholder без `user_id`.

## Красная шляпа (ощущение пользователя)

«Я удалил ребёнка, а сервер показывает старого и не даёт добавить» — ощущение поломки приложения; источник правды должен быть сервер, а ответы API — совпадать с тем, что сделал клиент.

## Жёлтая шляпа (плюсы выбранного направления)

- Реальное удаление аккаунта в БД + каскад по семьям владельца устраняет ложный «успех» delete.
- Правило «владелец семьи = может add/remove ростер» устраняет класс 403 при корректных данных.
- Reconcile для free + `user_id IS NULL` убирает «залипший» единственный child-shell без живого пользователя.

## Чёрная шляпа (риски)

- `DELETE FROM users` может упереться в внешние FK, не учтённые в скрипте — ответ 409/500 и необходимость расширить порядок удаления.
- Слот с `user_id NULL` после удаления **привязанного** аккаунта без вызова `family/remove` теоретически может остаться (если никогда не связали `user_id`) — продукт: явное удаление из ростера или будущая связка по событию.

## Зелёная шляпа (альтернативы / дальше)

- Явный `POST /api/family/unlink-placeholder` или обязательный `memberId` в теле delete child.
- Единый «FamilyRosterService» на бэкенде: все мутации ростера проходят одну валидацию инвариантов.

## Синяя шляпа (процесс и туду)

1. Выкатить изменения `user.py`, `family.py`, `family_roster_reconcile.py` на прод по внутреннему гайду (health → backup → scp → py_compile → restart → health).
2. Смоук: delete тестового пользователя → `GET /api/family/members` → `POST /api/family/add`.
3. SQL-аудит проблемных `FAM_*` после выката.
4. iOS: при успешном delete не показывать успех, пока не пришёл 2xx и при необходимости обновлён ростер (уже ближе к UX-политике).

## Реализовано в репозитории (код)

- `app/routers/user.py`: транзакционное удаление строк пользователя и связанных сущностей (см. файл).
- `app/routers/family.py`: `_actor_can_manage_family_roster`, использование в `add` / `remove`; вызов reconcile sole-child в `POST /api/family/reconcile`.
- `app/services/family_roster_reconcile.py`: promote sole placeholder child при `free`, если `user_id IS NULL`.
