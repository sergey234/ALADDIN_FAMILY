## 1. Зафиксированные продуктовые решения

### 1.1. Позиционирование

Используем следующий основной вариант:

**ALADDIN X AI — семейная платформа цифровой безопасности и воспитания.**

Приложение помогает родителям защищать детей в цифровой среде, устанавливать правила использования устройств, применять возрастные ограничения и управлять системой поощрений за полезные действия и выполненные задачи.

Основные возможности:

- родительский контроль и возрастные ограничения;
- семейные профили для родителей, детей, подростков и пожилых;
- система заданий, достижений, вознаграждений и согласованных ограничений;
- проверка подозрительных сообщений, ссылок, аудио и видео;
- закрытый семейный чат;
- семейные уведомления и экстренная связь;
- помощь при чрезвычайных ситуациях;
- функции помощи на автодорогах;
- детский образовательный раздел;
- упрощённый интерфейс для пожилых;
- AI-герои-ассистенты: Единорог, Аладдин и Джин.

Герои помогают ребёнку понимать правила цифровой безопасности, выполнять семейные задания, развивать полезные привычки и получать понятные возрастные объяснения. Это виртуальные AI-персонажи, а не живые консультанты.

Для текста Apple используем формулировки «вознаграждения и согласованные ограничения» или «поощрения и семейные правила». Формулировка «система наказаний» нежелательна для детского продукта.

### 1.2. Оплата в App Store

Выбран отдельный compile-time режим `APP_STORE_BUILD`.

В App Store-сборке:

- `useAlternativePayments = false`;
- `useIAP = true`;
- российская оплата не компилируется в пользовательский поток;
- `PaymentQRScreen` недоступен из навигации и deep links;
- нет QR, СБП, SberPay, банковских реквизитов и перехода на сайт для покупки цифровой подписки;
- Terms, FAQ и локализация App Store-сборки не предлагают внешнюю оплату;
- все цифровые подписки приобретаются только через StoreKit 2.

Код российской оплаты можно сохранить в репозитории для отдельного законного канала распространения. В App Store-бинарнике он должен быть недоступен технически, а не только визуально скрыт.

Вместе со сборкой отправляются:

- `ai.aladdin.subscription.individual.v2`;
- `ai.aladdin.subscription.family`;
- `ai.aladdin.subscription.premium`.

Дополнительный backend-флаг может использоваться только как fail-safe. Он не заменяет compile-time изоляцию.

## 2. Простое объяснение технических пунктов

### 2.1. Family Controls

Family Controls — официальный механизм Apple для управления Screen Time, выбора приложений ребёнка, расписаний и системных экранов блокировки.

Простой экран с тумблерами внутри ALADDIN сам по себе не может ограничивать другие приложения. Без разрешения Apple приложение может сохранить выбранные настройки и показать их пользователю, но iOS не обязана применять реальную системную блокировку.

Для полноценной реализации нужны:

1. Family Controls capability в основном target.
2. Разрешение Apple Family Controls Distribution для App ID `ai.aladdin`.
3. Screen Time extensions, если используются системные расписания и экраны блокировки:
   - Device Activity Monitor;
   - Shield Configuration;
   - Shield Action — если нужен обработчик действий на shield-экране;
   - Device Activity Report — только если нужен системный отчёт Screen Time.
4. Отдельные Bundle ID для каждого extension.
5. Отдельный запрос Distribution entitlement для каждого App ID/extension, использующего Family Controls.
6. Новые App Store provisioning profiles после одобрения Apple.

Как запросить:

1. Открыть Apple Developer Account.
2. Перейти в Certificates, Identifiers & Profiles.
3. Открыть Identifiers и выбрать App ID `ai.aladdin`.
4. Включить Family Controls capability.
5. На официальной странице Apple «Configuring Family Controls» перейти к запросу Family Controls entitlement для Distribution.
6. В заявке простыми словами описать:
   - приложение предназначено для семей;
   - родитель добровольно выбирает приложения и ограничения;
   - ребёнок не может снять родительские ограничения без родителя;
   - данные Screen Time не используются для рекламы и слежения;
   - функции имеют понятное объяснение и согласие;
   - в приложении предусмотрен способ отключить контроль.
7. После создания extension targets зарегистрировать их Bundle ID и подать отдельные запросы для каждого extension, которому нужен entitlement.
8. После одобрения пересоздать provisioning profiles и проверить подписанный Archive.

Официальный источник:

- https://developer.apple.com/documentation/xcode/configuring-family-controls

До одобрения entitlement нельзя обещать Apple фактическую блокировку сторонних приложений. Можно честно описывать доступные семейные правила, задания, вознаграждения, локальные настройки и образовательные функции.

### 2.2. APNs

APNs — сервис Apple для push-уведомлений.

Чтобы push работали в App Store:

1. В Xcode открыть основной target ALADDIN.
2. В Signing & Capabilities добавить Push Notifications.
3. Добавить Background Modes и отметить Remote notifications.
4. Убедиться, что Push Notifications включены для App ID в Apple Developer Account.
5. Пересоздать App Store provisioning profile.
6. Собрать Archive.
7. Проверить entitlements именно подписанного `.app`.

Почему проверяется Archive: исходный `.entitlements` показывает намерение проекта, а provisioning profile определяет, что Apple реально разрешила подписанной сборке. Для production push в итоговой подписи ожидается `aps-environment = production`.

### 2.3. DNS-защита

`NEDNSSettingsManager` позволяет приложению установить системную конфигурацию зашифрованного DNS — DNS-over-HTTPS или DNS-over-TLS. Пользователь затем сам включает её в системных настройках.

Это не полноценный VPN и не Packet Tunnel.

#### Результат проверки проекта 9 сентября 2026

Полноценный VPN действительно удалён:

- в Xcode-проекте нет Packet Tunnel target;
- нет Packet Tunnel app extension;
- основной `ALADDIN.entitlements` не содержит VPN entitlement;
- активный `NetworkProtectionManager` не импортирует NetworkExtension;
- код `NETunnelProviderManager` и запуска VPN-туннеля закомментирован;
- старый `VPNManager.swift` находится только в архивной папке `CLEAN_EXPORT2_20251031_000057`.

Но очистка завершена не полностью:

- `DNSProtectionManager.swift` входит в основной target, импортирует NetworkExtension и вызывает `NEDNSSettingsManager`;
- доступные экраны Family вызывают `enableProtection()` и `disableProtection()` для Smart DNS;
- экран `03_NetworkProtectionScreen.swift` всё ещё показывает кнопку подключения, выбор VPN-подобных серверов и состояние соединения, хотя `connect()` возвращает ошибку «Защита сети недоступна»;
- в production-локализации остаются заявления о скрытии IP, шифровании всего трафика, AES-256-туннеле, Kill Switch, серверах и безлимитной защите сети;
- `NetworkProtectionManager` содержит локальные демонстрационные серверы и фиксированные статистические значения.

Следовательно, технического VPN в приложении нет, но интерфейс и тексты всё ещё могут создать у пользователя и App Review впечатление, что VPN существует. Это риск Guidelines 2.1, 2.3 и 5.4.

#### Выбранное решение для первой повторной отправки

Для `APP_STORE_BUILD`:

1. Оставить Safari Content Blocker.
2. Не включать системный Smart DNS.
3. Не инициализировать и не вызывать `NEDNSSettingsManager`.
4. Скрыть Smart DNS cards и переключатели.
5. Убрать VPN-подобную кнопку «Подключить», выбор серверов, Kill Switch, auto-connect, трафик и uptime.
6. Убрать из активной RU/EN локализации заявления о VPN, скрытии IP и шифровании всего трафика.
7. Убрать VPN/безлимитный трафик из описаний тарифов.
8. Переименовать пользовательский раздел «Защита сети» в «Центр защиты» или «Цифровая защита».
9. Оставить в разделе реальные функции: Safari Content Blocker, Antifake, проверку файлов/ссылок, Call Directory, безопасность устройства, дорожную помощь и экстренную связь.

Исходный DNS-код можно сохранить для отдельного будущего релиза. Возвращать Smart DNS в App Store следует только после добавления `dns-settings`, корректного provisioning profile и проверки на физическом устройстве.

Для App Store нужен:

- Network Extensions capability;
- entitlement `com.apple.developer.networking.networkextension`;
- значение `dns-settings`;
- provisioning profile, содержащий этот entitlement.

По документации Apple для `NEDNSSettingsManager` отдельный DNS extension target не обязателен: встроенный системный протокол настраивается основным приложением. Пользователь должен явно включить конфигурацию.

Официальные источники:

- https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.networking.networkextension
- https://developer.apple.com/documentation/networkextension/dns-settings

Если entitlement не удаётся получить или функция не готова, App Store-сборка должна оставить только Safari Content Blocker и не обещать VPN или системную DNS-защиту.

### 2.4. Privacy Manifest

`PrivacyInfo.xcprivacy` — техническая декларация внутри приложения. Она сообщает Apple:

- какие категории данных собирает приложение;
- для чего они используются;
- связаны ли они с пользователем;
- используются ли они для межсервисного отслеживания;
- какие системные API, требующие объяснения причины, использует приложение.

Privacy Manifest не даёт приложению новых разрешений и сам не показывает системные окна. Он должен честно описывать уже существующее поведение.

После создания Archive Xcode объединяет manifest приложения и manifests сторонних SDK. В Organizer можно выбрать **Generate Privacy Report**. По этому отчёту заполняется App Store Connect → App Privacy.

Текущий manifest уже содержит:

- другой пользовательский контент;
- номер телефона;
- аудио;
- фотографии и видео;
- UserDefaults;
- File Timestamp.

Требуется проверить и, если данные действительно отправляются с устройства, добавить:

- Device ID или User ID;
- precise/coarse location;
- product interaction или other usage data;
- crash data;
- performance data;
- other diagnostic data;
- email — только если production-вход по email реально доступен;
- сообщения семейного чата и AI-текст как User Content;
- файлы и вложения;
- данные взаимодействия с AI.

Для каждой категории нужно определить:

- отправляется ли она за пределы устройства;
- связана ли она с JWT, family ID, member ID или device ID;
- используется ли только для App Functionality либо также для Analytics;
- срок хранения;
- возможность удаления.

Важно: если данные связаны на сервере с псевдонимным JWT/device ID, нельзя автоматически отмечать их как `Linked = false`. Сначала проверяется backend-модель.

Официальные источники:

- https://developer.apple.com/documentation/bundleresources/privacy-manifest-files
- https://developer.apple.com/documentation/bundleresources/describing-data-use-in-privacy-manifests
- https://developer.apple.com/app-store/app-privacy-details/

### 2.5. Зачем убирать неиспользуемые строки из Info.plist

Apple не прислала отдельное требование удалить Apple Music, HomeKit, Calendar, Bluetooth, Reminders или Siri.

Сами строки обычно не показывают системный запрос разрешения. Запрос появляется, когда приложение вызывает соответствующий API.

Но лишние строки нежелательны:

- создают впечатление, что приложение собирает больше данных, чем заявлено;
- вызывают дополнительные вопросы App Review;
- усложняют Privacy Label;
- скрывают настоящие необходимые разрешения среди устаревших;
- могут выглядеть как незавершённая или шаблонная конфигурация.

Если владелец не хочет удалять их сейчас, допустимый компромисс:

1. Не запрашивать эти разрешения в runtime.
2. Не упоминать неработающие функции в маркетинге.
3. Зафиксировать, для какой будущей функции нужен каждый ключ.
4. Перед каждой отправкой проверять, что приложение не показывает лишние permission prompts.

Лучший вариант для App Store — оставить только реально используемые разрешения. Это не удаление функций: строку легко вернуть одновременно с реализацией соответствующей функции.

## 3. Регистрация и пользовательские данные

Нельзя писать «приложение не использует персональные данные вообще». По определениям Apple идентификатор устройства, геолокация и пользовательский контент относятся к пользовательским данным, даже если пользователь не сообщает настоящее имя.

Корректная формулировка:

> Для начала использования ALADDIN X AI пользователю не требуется предоставлять имя, фамилию, номер телефона, email, пароль, дату рождения или документы. При первом запуске приложение автоматически создаёт псевдонимную техническую сессию устройства и получает JWT-токен.
>
> Для семейной настройки пользователь выбирает роль, возрастную группу и букву псевдонима. Приложение создаёт случайный идентификатор семейной группы, идентификатор участника и recovery code.
>
> JWT-токены и recovery code хранятся в iOS Keychain. Данные не используются для рекламы, продажи третьим лицам или рекламного профилирования.
>
> Геолокация, камера, микрофон, фотографии, файлы и контакты используются только после соответствующего действия пользователя и системного разрешения, когда оно требуется.

Фактические данные основной регистрации:

- identifierForVendor или другой технический device ID;
- тип устройства;
- семейная роль;
- возрастной диапазон;
- буква псевдонима;
- family ID;
- member ID;
- JWT access/refresh token;
- recovery code;
- технические anti-abuse сигналы trial — требуют отдельной проверки перед Privacy Label.

Это псевдонимная модель регистрации без обязательных ФИО, email и телефона, но не полное отсутствие пользовательских данных.

## 4. Пользовательский контент и семейный чат

В закрытом семейном чате пользователи могут отправлять текст, изображения, видео, голосовые сообщения и файлы. Публичной ленты и контакта с незнакомыми пользователями нет.

До отправки Apple необходимо выбрать и реализовать безопасную модель:

1. Жалоба на сообщение или участника.
2. Блокировка либо ограничение участника.
3. Родительское управление составом семейной группы.
4. Понятный контакт поддержки.
5. Правила допустимого контента.
6. Серверная обработка жалобы с идентификатором и статусом.

Удаление собственного сообщения не считается полноценным механизмом жалобы.

Для закрытой семьи рекомендуемый UX:

- «Пожаловаться» — отправляет минимальный пакет модерации;
- «Ограничить участника» — доступно родителю;
- «Удалить из семьи» — отдельное подтверждаемое действие родителя;
- ребёнок может пожаловаться родителю/администратору семьи;
- экстренные сообщения не блокируются без понятного предупреждения.

Эти действия должны быть показаны в видео Apple.

### 4. Внешние сервисы, инструменты и платформы

Приложение использует:

- собственный backend ALADDIN на `https://aladdin-ai.ru` — регистрация устройства, семейные функции, синхронизация, Antifake и AI;
- Apple StoreKit 2 — покупка, проверка и восстановление подписок;
- Apple Push Notification Service — семейные и защитные уведомления;
- Apple Family Controls, Managed Settings и Device Activity — родительские ограничения `[ОСТАВИТЬ ТОЛЬКО ПОСЛЕ ОДОБРЕНИЯ ENTITLEMENT И DEVICE QA]`;
- Apple Safari Content Blocker — фильтрация выбранных категорий сайтов;
- Apple Call Directory — локальное отображение предупреждений о подозрительных номерах;
- Apple Speech Recognition — распознавание речи;
- Apple Maps — открытие выбранной пользователем геолокации;
- RiveRuntime — локальное отображение анимаций персонажей;
- Telegram — только добровольное обращение пользователя в поддержку;
- AI/LLM: backend ALADDIN использует Hermes/OpenRouter; модель по умолчанию — DeepSeek V4 Flash. Google Gemini реализован только как опциональный fallback и по умолчанию выключен.
- STT: Apple Speech Recognition на устройстве/через системный сервис Apple; серверный fallback — Yandex SpeechKit, затем OpenAI Whisper.
- TTS: системный Apple AVSpeechSynthesizer; premium server TTS — ElevenLabs Flash.

AI-запросы обрабатываются через backend ALADDIN. Передача AI-текста происходит после согласия пользователя. Приложение не содержит рекламы и рекламных SDK и не использует пользовательские данные для рекламного отслеживания.

Перед отправкой письма список должен быть подтверждён runtime-проверкой production feature flags: локальный аудит доказывает исполняемый маршрут и defaults, но не наличие/активность production credentials.
