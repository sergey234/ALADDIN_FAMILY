# План: выравнивание семьи / тарифа iOS ↔ сервер (100% + защита от рассинхрона)

Документ фиксирует причины инцидента (JWT/клиент «trial, 3 места» vs `POST /api/family/add` → **409 `family_roster_full`** при **2** членах в БД), неопределённость по **DELETE /remove**, и пошаговую реализацию так, чтобы **источник правды был один**, а клиент **не обещал больше, чем разрешит API**.

---

## 1. Зафиксировать проблемы (по пунктам)

| # | Симптом | Вероятная причина | Зона ответственности |
|---|---------|-------------------|----------------------|
| 1 | Главная: «триал, 2 из 3», добавить нельзя | Лимит на UI из **JWT/локального** `SubscriptionManager`; gate на `add` — из **`users.subscription_level` владельца** в Postgres. После `cancel` / смены тарифа БД и JWT расходятся. | Бэкенд (запись уровня) + iOS (отображение лимита с сервера) |
| 2 | `POST /api/family/add` → **409** `family_roster_full` при 2 членах и «ожидаемых» 3 | `COUNT(family_members) >= max_family_slots_for_subscription_level(DB owner level)`; для владельца в БД уровень **не trial** (например `free` → max **1**, или `personal` → **2**). | Бэкенд + данные |
| 3 | Удаление ребёнка «не получается» | В логах не было полного трейса **DELETE** `/api/family/remove` (статус + body). Возможны: запрос не ушёл, **4xx** (403/400/404), ушёл 200 но строка не удалена, UI не обновляет после ошибки. | iOS (логирование/UX) + проверка API |
| 4 | Повторение в будущем | Любая смена тарифа без **атомарного** обновления БД и без **единого контракта** «лимит ростера для UI» с сервера. | Архитектура + процессы |

---

## 2. Принципы (архитектура «как в зрелых продуктах»)

1. **Единый источник правды для лимита ростера:** число слотов и «эффективный» тариф для **семьи** определяются **сервером** (БД + бизнес-правила), а не только JWT.
2. **JWT** — удобный кэш для офлайна и быстрого UI, но **после любого действия, меняющего подписку** (trial, cancel, IAP), клиент **обязан** получить согласованное состояние с сервера (или явный ответ об ошибке синхронизации).
3. **Ошибки API** (`409 family_roster_full`, `403`, …) должны **декодироваться** и превращаться в **понятный текст + действие** (обновить тариф / повторить синхронизацию), а не в «молча не добавилось».
4. **Наблюдаемость:** один корреляционный `request_id` / `family_id` / `user_id` в логах клиента и сервера для цепочки cancel → sync → add/remove.

## 3. Ветка A — Бэкенд (устранение первопричины)

### 3.1. Инвариант данных

- При **`POST /api/auth/register-device-trial`**, **`POST /api/subscription/cancel`**, webhooks IAP / смена плана — **всегда** обновлять **`users.subscription_level`** (и при необходимости `subscription` JSON / даты) для **того же `user_id`**, что в JWT.
- Чеклист выката: после cancel в приложении — **SQL smoke** (или admin script): `SELECT id, subscription_level FROM users WHERE id = ?` совпадает с ожидаемым уровнем после действия.

### 3.2. Семья и владелец

- Убедиться, что **`families.owner_user_id`** всегда указывает на пользователя, для которого актуален тариф (у вас gate читает уровень **владельца** семьи).
- Если в продукте «владелец = тот, кто создал семью», при передаче владения (если бывает) — обновлять `owner_user_id` и документировать.

### 3.3. Явный API «лимит ростера для текущего пользователя» (рекомендуется)

Добавить **одно** из (или оба, по этапам):

- **Вариант 1 (минимальный):** расширить **`GET /api/family/stats`** полями вроде  
  `familyRosterUsed`, `familyRosterMax`, `familyRosterTier` (строка уровня, по которому посчитан max), все из **того же кода**, что и gate на `add` / `join`.
- **Вариант 2:** отдельный лёгкий **`GET /api/family/roster-cap`** (тот же смысл, меньше полей).

Плюсы: iOS рисует «X из Y» **с сервера**; при расхождении JWT и БД пользователь видит **реальный** потолок.

### 3.4. Заголовки (уже в roadmap гайда)

- Выдавать **`X-Family-Roster-Max`** / **`X-Family-Roster-Used`** (или аналог) на **`GET /api/family/members`** и/или **`stats`**, чтобы клиент мог обновить счётчики **без** парсинга тела stats, если удобнее.

### 3.5. Gate на `add` / `join` (уточнение политики)

- Зафиксировать в доке: лимит = **`max_family_slots_for_subscription_level(owner DB level)`**; при желании добавить **второй источник** только как **диагностику** (лог warning, если JWT claim `subscription.level` ≠ DB для того же user).
- Опционально: при **409** добавлять в JSON поле `server_subscription_level`, `roster_count`, `roster_max` — ускоряет поддержку (без SQL).

### 3.6. DELETE remove

- Убедиться, что в **prod-логах** (structlog) пишутся `member_id`, `family_id`, `user_id`, HTTP результат.
- Проверить сценарии: последний parent, self-removal, чужой `memberId` — и что iOS шлёт **ровно** id из `GET /members`.

## 4. Ветка B — iOS (устойчивое поведение и UX)

### 4.1. Источник «X из Y» на главной и в семье

- Ввести явную модель вроде **`FamilyRosterQuota`** (used, max, tierSource: `server` | `unknown`).
- **После:** `register-device-trial`, `subscription/cancel`, успешного IAP, входа на главную / экран семьи — **приоритетно** подтягивать квоту с **`GET /api/family/stats`** (или нового endpoint), затем обновлять `@Published` для UI.
- **`SubscriptionManager.familyMemberLimit`** использовать **только** если сервер ещё не ответил; после ответа — **перезаписывать** из `stats` (или не смешивать: показывать серверное как канон).

### 4.2. Обработка `409 family_roster_full` на add

- В `NetworkManager` / `APIService` уже есть тело `detail` — пробросить в **локализованное** сообщение:  
  «Семья уже заполнена по текущему тарифу на сервере. Обновите подписку или подождите синхронизации.»
- Кнопка «Повторить» = повторный **`syncWithServer`** + повторный fetch **stats/roster-cap**.

### 4.3. Удаление участника

- На подтверждение delete: логировать **URL, status, `detail`, `memberId`** (одна строка в MasterLogger).
- При **не-200**: не удалять локально; показывать alert с `detail`.
- После **200**: как сейчас — `syncFamilyMembersFromAPI` + обновление stats.

### 4.4. Симулятор vs устройство

- В логах был пропуск StoreKit — ок для dev; для проверки тарифа использовать **реальные** ответы **`/api/subscription/*`** и **stats**, а не только локальный mock.

### 4.5. Регрессии в UI

- Разделить в копирайте **«члены семьи»** и **«устройства»**, если на главной рядом (отдельная продуктовая задача), чтобы не путать с лимитом слотов.

## 5. Ветка C — Процессы и качество

### 5.1. Smoke и CI

- Расширить **`docs/FAMILY_API_SMOKE_REGIMEN.md`**: шаг «после cancel / trial» — **`SELECT subscription_level`** (или вызов admin) + **`GET stats`** с новыми полями + **`POST add`** до лимита и ожидаемый **409** на следующем.
- Автотесты бэкенда: unit на `max_family_slots` + integration на add при разных `users.subscription_level`.

### 5.2. Мониторинг

- Метрика/лог: счётчик **`family_add_roster_full`** с тегами `owner_level`, `jwt_level` (если доступен в контексте) — для отлова массового рассинхрона.

### 5.3. Версионирование API

- В ответе stats опционально `apiContractVersion` — клиент может предупредить «обновите приложение».

## 7. Критерии готовности (Definition of Done)

1. После **trial** на устройстве **`GET /api/family/stats`** (или эквивалент) показывает **max ≥ 3** для той же учётки, что в JWT, и **`POST /api/family/add`** принимает третьего до достижения max.
2. После **cancel → free** stats показывает **max 1** (или продуктово согласованное значение), add даёт **409** только когда реально полно — и текст на iOS понятен.
3. Удаление ребёнка: в логах виден **DELETE** с **200** и последующий **GET members** без этого id.
4. В доке зафиксирован **один** алгоритм лимита и кто владелец семьи для тарифа.
