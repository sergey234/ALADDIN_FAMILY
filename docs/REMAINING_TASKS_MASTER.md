## C) ML‑план: `audit-42-inventory` и `extended-42-verify` (идеально = 100%)

Здесь **два разных числа** — не «42+138 в одной таблице»:

| Что | Сколько | Тикет в плане | Где вести учёт |
|-----|---------|---------------|----------------|
| **Компоненты** (экраны/агенты с `component_id`) | **42** | `audit-42-inventory` | **`docs/audit/AUDIT_42_INVENTORY.md`** — таблица 1 (7 KPI) + таблица 2 (35 остальных) = **42 строки** |
| **Функции безопасности** (операции: вкл/выкл, скан, карантин, …) | **138** | `extended-42-verify` | **`docs/audit/EXTENDED_138_CHECKLIST.md`** — **138** строк (или группы с подстроками), по смыслу «BusinessOK» на проде |

### C1 — только **42** (`audit-42-inventory`)

- Файл: `docs/audit/AUDIT_42_INVENTORY.md`.
- Одна строка = один компонент из списка `ALL_42_COMPONENTS` (см. `docs/server/check_42_components_registry.py`).
- **100%:** у всех 42 заполнены цепочка экран → API → источник данных → SLA/владелец и статусы `inventory` / `verify` доведены до `ok` (где применимо).

### C2 — только **138** (`extended-42-verify`)

- Файл: `docs/audit/EXTENDED_138_CHECKLIST.md` (генерация: `python3 tools/gen_extended138_checklist.py` → ровно **138** строк таблицы).
- Здесь **не** дублируем 42: перечисляются **138** функций/операций (как в продуктовой модели и старых отчётах по 138).
- **100%:** для каждой функции — прод‑проверка по смыслу (не только «эндпоинт ответил 200»), отмечено в таблице.

**Порядок работ:** логично сначала довести **C1 (42)**, чтобы знать откуда данные у компонентов; параллельно или следом наполнять **C2 (138)** по группам (родительский контроль, угрозы, отчёты и т.д.).
