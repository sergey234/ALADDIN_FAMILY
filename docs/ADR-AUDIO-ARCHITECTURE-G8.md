# ADR: границы аудио-модуля (G8)

**Статус:** accepted  
**Дата:** 2026-04-27  
**Связь:** `docs/GAP_CLOSURE_PLAN_PHASES_1_8_ML_HANDOFF.md` (G8, G9), `Core/Audio/AudioManager.swift`, `Core/Audio/SoundEffectPlayer.swift`

## Контекст

Фоновая музыка, SFX и возможные детские сценарии (караоке, сказки) требуют **разделения ответственности**. В плане зафиксирован риск смешения в одном «бог-модуле».

## Решение

1. **Канон границ на ближайшие релизы:**
   - **`SoundEffectPlayer`** — короткие SFX, приоритет/антиспам на уровне плеера, без бизнес-логики экранов.
   - **`AudioManager`** — фон/сессии/ducking и координация с системой; **не** содержит доменных правил конкретного экрана (квест, награда и т.д.) — экран дергает узкий API.
   - Потоковое/длинное аудио для контента (сказки, уроки) — через **отдельный** слой воспроизведения в модуле experience (`ChildContentExperienceScreen` и вложенные view), поверх общих утилит громкости/прерывания по необходимости.

2. **Новый код:** не добавлять в `AudioManager` предметно-зависимые ветки; выносить в `SoundEffectPlayer` или в локальный контроллер сцены.

3. **G9 (ассеты):** гейт `scripts/validate_app_sound_effects.py` в CI остаётся обязательным для изменений набора звуков; расширение библиотеки — только с обновлением скрипта/бандла.

## Следующий шаг (не блокер релиза ADR)

При росте сложности — выделить тонкий фасад **`AppAudioSession`** (или аналог) с единым входом для «кто сейчас владеет аудио»; отдельный ADR при появлении конфликтов сессий между экранами.

## Последствия

- Ревью: любой PR, расширяющий `AudioManager` бизнес-ветвлениями, отправляется на доработку согласно этому ADR.  
- G8 в gap-трекере трактуется как **«политика архитектуры принята»**; полная миграция старого кода — отдельными задачами.
