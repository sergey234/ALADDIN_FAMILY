# 🛠️ План улучшения P95 при пиковых нагрузках

**Для:** следующая ML‑система  
**Дата:** 2025‑11‑27  
**Статус сейчас:** не критично (P95 ≈ 2.5 s только при экстремальной нагрузке 10 000 запросов / 1 000 одновременных; при реальных нагрузках P95 < 100 ms)  
**Причина:** на пике Nginx/SSL тратит до 1.5 s на установку соединений (см. `docs/REAL_ROOT_CAUSE_FOUND.md`).

---

## 📊 Текущие показатели

| Сценарий                               | P50 | P95  | Примечание                              |
|----------------------------------------|-----|------|----------------------------------------|
| 100 / 10 HTTPS                         | 6 ms | 11 ms | Отлично                                |
| 1 000 / 100 HTTPS                      | 65 ms | 91 ms | Отлично                                |
| 10 000 / 1 000 HTTPS                   | 778 ms | 2 481 ms | Приемлемо (было 8 258 ms)             |
| 10 000 / 1 000 HTTP (минуя Nginx)      | 410 ms | 1 026 ms | Показатель API Gateway                 |

Вывод: проблема осталась только при экстремальном HTTPS‑пике → фокус на Nginx/SSL.

---

## ✅ Что уже сделано

1. Добавлен `upstream api_gateway` + `keepalive 200`.
2. Таймауты縮ены (connect 10s, read/send 30s).
3. Proxy буферы увеличены (16k + busy 64k).
4. `ssl_buffer_size 16k`, `ssl_ecdh_curve auto`.
5. Подробный отчёт: `docs/NGINX_OPTIMIZATION_RESULTS.md`.

---

## 🔜 План дальнейших улучшений

### 1. SSL/TLS
| Шаг | Детали |
|-----|--------|
| 1.1 | Включить TLS session resumption c OCSP stapling (fast handshake). |
| 1.2 | Проверить `ssl_session_tickets` (в options-ssl-nginx.conf сейчас off) — при необходимости включить с rotate ключами. |
| 1.3 | Включить HTTP/2 (быстрее TLS, меньше соединений). |
| 1.4 | Рассмотреть TLSv1.3 0-RTT (если клиенты поддерживают). |

### 2. Connection Management
| Шаг | Детали |
|-----|--------|
| 2.1 | Убедиться, что `keepalive_requests`/`keepalive_timeout` оптимальны (сейчас 10 000 / 30s). При большом пике можно поднять timeout до 60s. |
| 2.2 | Настроить `proxy_cache_revalidate`/`proxy_cache_bypass` для health/metrics, чтобы снизить частоту обращений к API при истечении кэша. |
| 2.3 | Добавить мониторинг количества `CLOSE-WAIT` (цель < 5). |

### 3. Kernel / TCP
| Шаг | Детали |
|-----|--------|
| 3.1 | Проверить `net.ipv4.tcp_tw_reuse`, `tcp_fin_timeout`, `somaxconn` (увеличить до 1024/4096). |
| 3.2 | Включить `reuseport` для Nginx worker’ов (`listen ... reuseport`). |

### 4. API Gateway
| Шаг | Детали |
|-----|--------|
| 4.1 | Рассмотреть HTTP keepalive между Nginx и Uvicorn (уже включено). Следующий шаг — enable `http2` в Uvicorn/Gunicorn или переключиться на `hypercorn`. |
| 4.2 | Добавить метрики Prometheus по P95/P99, connect time, чтобы отслеживать в реальном времени. |

### 5. Инфраструктура
| Шаг | Детали |
|-----|--------|
| 5.1 | Рассмотреть CDN/Edge (Cloudflare/NGINX Plus) — HTTPS завернётся на Edge → основному серверу достанутся HTTP (без TLS накладных). |
| 5.2 | Добавить auto-scaling (несколько upstream серверов + load balancer). |

---

## 📝 Чек‑лист для запуска следующей ML‑системой

1. **Поднять стенд** и повторить базовый тест (`ab -n 10000 -c 1000 https://aladdin-ai.ru/api/health`).
2. Если P95 > целевого:
   - Выполнить блок “SSL/TLS”.
   - Затем “Connection Management”.
   - После каждого шага прогонять тесты и писать в общий отчёт.
3. Финальная цель: P95 < 500 ms при 10 000 / 1 000.
4. Документировать изменения в `docs/NGINX_OPTIMIZATION_RESULTS.md`.

---

## Контрольные точки

- **Phase 1 (TLS session resumption + HTTP/2)** → целевой P95 < 1 500 ms.
- **Phase 2 (Kernel tuning + reuseport)** → целевой P95 < 800 ms.
- **Phase 3 (Edge/CDN или масштабирование)** → целевой P95 < 500 ms.

Готово к передаче: текущие показатели безопасны, а этот план позволит без пропусков довести систему до “идеального” уровня при следующих итерациях.  
Если понадобятся дополнительные метрики/скрипты — см. `docs/NGINX_OPTIMIZATION_RESULTS.md` и `docs/REAL_ROOT_CAUSE_FOUND.md`.
