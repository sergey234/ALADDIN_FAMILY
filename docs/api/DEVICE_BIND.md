# POST `/api/devices/bind`

Аутентификация: `Authorization: Bearer <access_token>` (как у остальных `/api/*`).

## Тело запроса (JSON)

Ожидается **хотя бы одно** из полей (пустые строки не отправлять):

| Поле | Тип | Описание |
|------|-----|----------|
| `token` | string, optional | Секрет из QR / deep link (`pairing_token` после `POST /api/devices`). |
| `pin` | string, optional | Ровно **6 цифр** (лишние символы игнорируются, берутся первые 6 цифр). |

Примеры:

```json
{ "token": "<pairing_token>" }
```

```json
{ "pin": "334329" }
```

Опционально оба поля (усиленный сценарий): `{ "token": "...", "pin": "334329" }` — при наличии `token` сервер сначала обрабатывает путь по токену.

## Ответы

- **200** — устройство привязано, `pairing_token` / `short_pin` очищены у строки в БД.
- **401** — нет или невалидный JWT.
- **404** — пара не найдена: неверный токен/PIN, истёк TTL для PIN-only (см. сервер `PAIRING_PIN_TTL_MINUTES`), уже использовано и нет следов для идемпотентности.
- **409** — повторная попытка bind **по тому же токену**, который уже был успешно использован (идемпотентность по `pairing_token_sha256`).
- **422** — не передан ни `token`, ни валидный `pin`.
- **429** — слишком много неудачных попыток bind с одного пользователя/IP (скользящее окно на сервере).

## Universal Links (https, B4)

Чтобы ссылки вида `https://<ваш-домен>/...?token=` открывали приложение без кастомной схемы:

1. Разместить **AASA** (`apple-app-site-association`) на домене (HTTPS, без редиректа).
2. В Xcode: Signing & Capabilities → **Associated Domains** → `applinks:<ваш-домен>`.
3. Клиент уже умеет вытаскивать `token` из https-URL в `DevicePairingLinkParser` при подходящем host/path (см. код).

## Связанные эндпоинты

- `POST /api/devices` — создаёт pending-устройство, возвращает `pairing_token`, `short_pin`.
- `GET /api/devices` — список устройств текущего пользователя (секреты pairing в ответе не отдаются).
