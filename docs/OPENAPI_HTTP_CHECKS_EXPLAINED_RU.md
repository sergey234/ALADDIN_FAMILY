# Проверка API простым языком: почему был «шум» 404/422 и как сделать правильно

## Аналогия

Представь, что у каждой двери в здании написано: **«только вход с ключа X»** или **«только выход»**, а на двери ещё табличка **какой документ положить на стол** (тело запроса).

Если ты **ко всем дверям подходишь одинаково** — например, везде пытаешься **втолкнуть один и тот же пакет через POST**, то:

- на двери, где разрешён только **GET**, сервер честно скажет **«такого маршрута для POST нет»** → часто **404** или **405 Method Not Allowed**;
- на двери, где нужен **другой JSON** (другие поля), сервер скажет **422** — «данные не подходят под схему».

Это **не доказательство**, что «бэкенд сломан». Чаще это доказательство, что **тест был наивным**: не тот **HTTP-метод** и не то **тело**.

## Правильная проверка «всех эндпоинтов, которые реально есть на сервере»

### 1) Источник правды — **OpenAPI** (`/openapi.json`)

На прод-стенде **`http://149.154.65.180:8002/openapi.json`** отдаёт полный список **путей и методов** (GET/POST/…), как их зарегистрировал FastAPI.

У публичного домена **`https://aladdin-ai.ru`** в текущей конфигурации **часто нет** открытого `openapi.json` (даёт **404**) — поэтому для **полного** списка операций используй **тот же бэкенд**, где лежит OpenAPI (см. `ALADDIN_BASE_URL` ниже).

### 2) Скрипт **с правильными методами** (рекомендуемый smoke)

- **Файл:** `scripts/openapi_conformant_audit.py`
- **Что делает:** читает OpenAPI и для **каждой** пары `(путь, метод)` шлёт запрос **именно этим методом**. Если в схеме объявлен JSON-body — шлёт **минимальный** `{}` (многие ручки ответят **422** — это нормально: маршрут найден, не хватает полей).
- **Авторизация:** `POST /api/auth/register-device` с `device_id` + `deviceType`, далее `Authorization: Bearer …`.
- **Актуальный прогон (UTC 2026-04-25):** см. `docs/OPENAPI_CONFORMANT_AUDIT_LATEST.md` и `docs/OPENAPI_CONFORMANT_AUDIT_LATEST.json` (или timestamp-файл рядом).

**Краткие цифры последнего прогона:**

| Метрика | Значение |
|--------|----------|
| Операций в OpenAPI (учтены все методы) | **395** |
| Не **404** (маршрут «откликнулся» иначе) | **316** / 395 |
| Успех **2xx** | **192** |
| **422** (схема/валидация при минимальном теле) | **121** |
| **404** | **79** (часто нет сущности с тестовым id — это другой смысл, чем «нет маршрута у POST везде») |
| **5xx** | **1** |

**Найденный 5xx в этом прогоне:** `GET /api/gamification/rewards/history` → **500** (см. JSON-отчёт, поле `results` с `status: 500`). Это уже **сигнал для бэкенда**, а не артефакт «не тот метод».

```bash
ALADDIN_BASE_URL=http://149.154.65.180:8002 \
  python3 scripts/openapi_conformant_audit.py
```

### 3) `smart_api_tester.py` — зачем он, если он «грубый»

- Удобен как **быстрый дым** с настоящим HTTP, но стратегия «один POST + один JSON на всех» **не равна** OpenAPI-контракту.
- Имеет смысл **только** вместе с пояснением выше; **не** как единственный % «готовности API».

### 4) `docs/server/full_system_endpoint_audit.py` — «релизный» аудит другого типа

- Делает **узкий** safe-режим (в типичной конфигурации — в основном **GET** + политика **без mock / без 503-обхода / без JWT в URL**).
- Это **другой** набор критериев, чем «прогнать все методы с минимальным телом». Оба подхода дополняют друг друга.

## Итог

- **Правильная** автоматическая проверка «что на сервере задекларировано» = **OpenAPI + реальные вызовы с верными методами** → `scripts/openapi_conformant_audit.py`.
- **422** при минимальном теле — обычно **нормально** (нужен реальный business-payload).
- **404** после наивного POST — чаще всего **про ошибку теста**, а не про «эндпоинта нет».
- Отдельно смотрите **5xx** в отчёте — это реальные кандидаты на фикс на бэкенде.
