## Зачем два плана

| План | Цель | Артефакты |
|------|------|------------|
| **A** | Качество Telegram-бота: тесты, эксплуатация, UX, комплаенс-минимум | runbook, pytest, CI, логи, политика данных… |
| **B** | Партнёрский HTTP API (аналог идеи [Wizard API](https://api.wizard-bot.com/docs/)): ключи, заказы, пополнения | OpenAPI, FastAPI, БД, ключ в боте |

Оба плана используют одну БД магазина (`shop.db`), но **разные релизы** и **разные риски**. Порядок старта согласован ниже.

---

## Метод «шесть шляп» (сжато)

- **Белая:** факты — SQLite, aiogram, заказы/ledger/topup; партнёрам нужен REST + ключ.  
- **Красная:** страх утечки ключа → маска, ротация, предупреждения, server-to-server.  
- **Жёлтая:** ценность — конструкторы без форка бота; один основной бот + реф-ссылка.  
- **Чёрная:** SQLite под высокий RPS; дубли заказов без идемпотентности; логирование секретов.  
- **Зелёная:** v2 — вебхуки, Postgres, субаккаунты; не смешивать с v1.  
- **Синяя:** порядок фаз B0→… и параллель с A — этот документ.

## План B0 — решения (зафиксировано до реализации HTTP)

1. **`orders.user_id`** для заказов, созданных по API, = **`api_clients.owner_user_id`** (владелец ключа).  
2. **Получатель** Stars/Premium в API = строка в **`user_note`** (как в боте), после нормализации `@username`.  
3. **`orders.source`** = `telegram` | `api`.  
4. **Идемпотентность:** заголовок **`Idempotency-Key`** (UUID); уникальность на уровне БД `(api_client_id, idempotency_key)` при непустом ключе.  
5. **Секреты:** в БД только **`key_hash`** + **`key_prefix`** для отображения; сырое значение ключа показывается пользователю **один раз** при выпуске (реализация в фазе B5).  
6. **Партнёрский фронт:** ключ только **сервер-сервер**; не встраивать в публичный браузерный JS.  
7. **Комиссия рефоводу** при `completed` для `source=api` — отдельное правило (документ + код в `order_flow` или отдельном хуке), не ломая текущую рефералку бота.

1. **B0** — этот раздел (готово в MD).

4. **Параллельно:** **B3–B4** (FastAPI, эндпоинты) и **часть A** (pytest, структурные логи).  
5. **B5** — выдача/ротация ключа в боте.  
6. **B6** — док для партнёра, «золотой путь», пример server-to-server.

## Проверка полноты (что явно предусмотрено)

- Разделение **telegram vs api** по полю `source`.  
- **Идемпотентность** и уникальный индекс.  
- **Безопасность ключа** (hash, prefix, не логировать секрет).  
- **CORS / размещение ключа** — в runbook B и в доке партнёра.  
- **Миграции** для старых БД без новых колонок.  
- **Параллельность A и B** без блокировки: после B2 бот может работать как раньше (новые колонки с default).  
- **Postgres / вебхуки / автоплатежи** — вынесены в v2 или в план A (автоплатежи), чтобы v1 завершался измеримо.

## Запуск Partner API (прод)

Из каталога `telegram_stars_shop_bot/` (нужны `.env` или переменные окружения: `BOT_TOKEN`, `ADMIN_IDS`, **`API_KEY_PEPPER`**, при необходимости `DATABASE_PATH`, `PARTNER_API_CORS_ORIGINS`):

```bash
python3 -m partner_api.main
```

По умолчанию слушает `0.0.0.0:8090`. Документация интерактивно: `http://<хост>:8090/docs`. OpenAPI-файл: `docs/openapi_v1.yaml`.

**Ключ:** в боте раздел «Наш API» → «Partner API (X-API-KEY)» → выпуск ключа (после задания `API_KEY_PEPPER`).

Уведомления админам в Telegram при создании заказа/пополнения через API используют тот же `BOT_TOKEN`, что и бот (кнопки как в боте).
