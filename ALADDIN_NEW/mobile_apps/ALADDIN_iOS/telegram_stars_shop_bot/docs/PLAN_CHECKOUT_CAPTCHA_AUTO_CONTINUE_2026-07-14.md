# План: после капчи — сразу счёт (без повторного «Оплатить»)

**Дата:** 2026-07-14  
**Цель UX:** после успешной checkout-капчи пользователь **сразу** получает счёт / оплату, без повторного клика.  
**Cursor TODO SSOT:** `CHECKOUT_CAPTCHA_AUTO_CONTINUE_TODO_TRACKER.md` (ids `cc-*`)  
**Связано:** `BOT_ARCHITECTURE_REFERENCE_RU.md` (§ checkout + captcha), `shop.py` `order_submit`, `common.py` `checkout_captcha_pick`.

---

## 1. Проблема (факт в коде)

Сейчас:

1. Пользователь нажимает **«Создать заказ»** (`order:submit`).
2. Нет валидного `checkout_captcha_ok_until` → `prompt_checkout_captcha`.
3. Успех в `checkout_captcha_pick` → TTL продлевается → alert **«Готово! Нажмите „Подтвердить заказ“ ещё раз.»**
4. Счёт **не** создаётся, пока пользователь снова не нажмёт кнопку.

Это лишний шаг и потеря конверсии.

Горячие точки:

| Файл | Что делает сейчас |
|------|-------------------|
| `bot/handlers/shop.py` → `order_submit` | гейт капчи → `return` без создания заказа |
| `bot/handlers/common.py` → `checkout_captcha_pick` | только `extend_checkout_captcha` + текст «нажмите ещё раз» |
| `users.checkout_captcha_ok_until` + `CHECKOUT_CAPTCHA_TTL_SECONDS` | окно «капча уже ок» (по умолчанию ~15 мин) — **оставить** |

---

## 2. Наилучшее решение (канон)

### 2.1 Автопродолжение, а не новый «мастер»

Не плодить второй платёжный сценарий. После успеха капчи **вызвать тот же finalize**, что и `order:submit`:

1. FSM по-прежнему `CheckoutStates.waiting_confirm` (product / payment / recipient в state).  
2. На успех `chk:c:*`:  
   - `extend_checkout_captcha` (как сейчас);  
   - удалить сообщение капчи;  
   - **сразу** вызвать общий helper `continue_checkout_after_captcha(...)` ≈ тело `order_submit` (создание заказа + экран счёта / ссылка оплаты).  
3. Пользователь **не** жмёт «Создать заказ» / «Оплатить» повторно.

### 2.2 Статус капчи на операцию

Уже есть `checkout_captcha_ok_until`:

- после успеха — не спрашивать капчу повторно, пока TTL жив и заказ в работе;  
- TTL env: `CHECKOUT_CAPTCHA_TTL_SECONDS` (не ломать);  
- опционально FSM-флаг `awaiting_checkout_after_captcha=1` в момент `prompt_checkout_captcha` — явный resume-intent (защита от «успех капчи без checkout-сессии»).

### 2.3 Отказы (счёт не создавать)

| Событие | Действие |
|---------|----------|
| Неверный эмодзи | alert «Попробуйте другой вариант»; challenge жив; **заказ не создавать** |
| Закрыл / игнор капчи | нет callback успеха → **заказ не создавать** |
| Протухла FSM-сессия | alert «Сессия устарела»; **заказ не создавать** |
| Капча ок, но FSM пустой | не вызывать finalize; короткое «вернитесь к заказу» |

### 2.4 Почему не альтернативы

| Вариант | Почему хуже |
|---------|-------------|
| Оставить «нажмите ещё раз» | текущая боль ТЗ |
| Убрать капчу совсем | регресс антифрода |
| Создавать заказ **до** капчи | pending-мусор + счёт без проверки |
| Дублировать весь `order_submit` в `common.py` | расхождение багов; нужен **один** helper |

---

## 3. Новый сценарий (продукт)

```
Оплатить / Создать заказ
  → капча ещё не ок? → показать капчу (заказ пока НЕ создан)
  → успех → автоматически создать заказ и отправить счёт / кнопки оплаты
  → повторный клик не нужен
  → в окне TTL капча не спрашивается снова на следующем submit той же/следующей оплаты
```

Тексты: убрать «Нажмите … ещё раз»; короткий toast «Проверка пройдена» (опционально) и сразу экран счёта.

## 4. Карта правок

| Слой | Действие |
|------|----------|
| `shop.py` | вынести core `order_submit` → `finalize_checkout_order(cb, state, …)`; гейт капчи без изменений по смыслу |
| `common.py` `checkout_captcha_pick` | после ok → вызвать `finalize_checkout_order` (нужен `FSMContext`, products, bot) |
| `emoji_captcha.prompt_checkout_captcha` | опционально: `state.update_data(awaiting_checkout_after_captcha=True)` |
| Тесты | успех капчи → заказ/счёт без второго callback; fail → нет заказа |
| Docs | этот план + архитектура §436 |

Inject middleware уже отдаёт `settings`, `conn`, `products` в handlers — подключить `state` в captcha handler.
